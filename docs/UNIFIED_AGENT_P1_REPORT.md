日期：2026-10-28。Git 基线：`7bb548b`；备份分支：`codex/backup-unified-p1-20261028`。

状态：已完成现有接口的首轮静态核对与隔离契约验证，并确定第一版实现路线。尚未实现统一调度器，也未进行新版场景、权限代理或迁移的端到端验收；不能将本文当作上线通过报告。

后续实施状态见 [统一主体实施记录](UNIFIED_AGENT_IMPLEMENTATION.md)；本文保留 P1 时点的结论与证据。

需求依据：[需求 v1.0](UNIFIED_AGENT_REQUIREMENTS.md)、[验证清单](UNIFIED_AGENT_VALIDATION_PLAN.md)。本轮只新增验证脚本及文档，没有改运行代码、生产配置、QQ 客户端、DSH 安装文件或真实会话。

## 1. 技术结论

第一版采用一个受限主 preset、一个持久化主 session、桥接统一收件箱和串行调度。场景切换只改变桥接当前场景及凭证，不调用 DSH 创建或切换 session。现有 SnowLuma 接口继续复用。

DSH 已有排队消息、请求编号去重、队列查询、事件订阅和受限独立工作会话所需基础能力。关键新增工作在桥接：持久化投递身份、场景资格、未读确认范围、动态工具授权及新旧调度交接。不能只把所有 key 映射到同一个 sessionId：旧代码仍按 key 并发排队、注入令牌及消费状态，会互相干扰。

文件自主判断按用户最新决定处理：Agent 依据可信来源及规则判断，不开发意图证明器，不设每次审批；程序执行身份、等级、路径及工具范围校验。

## 2. 已核对的协议事实

### V01：投递和等待

本机安装的 `@deepseek-ai/dsh-api-session-controller` 为 `0.2.1-rc.2`。核对位置：其 `lib/index.js` 中 `SessionCommandController.prompt`、`hasPromptRequest` 和 `cancel`；隔离测试直接加载同包 `lib/types/commands.js` 的实现，使用内存 host 服务，不连接正在运行的 DSH。

- `mode: queue` 调用 `agent.followup`，`steer` 调用 `agent.steer`。返回 `accepted: true` 仅表示接收，不表示回合完成或消息已经发送到 QQ。
- 相同 `requestId` 可在 next-turn、next-step 队列及已记录 user/message 中识别。顺序重试不会重复入队；相同正文配新编号会再次入队。
- 两次文字请求并发进入异步 admission 时，都可能在第一次入队前通过查重。测试确实观察到两次 followup。因此桥接必须串行提交，不能把服务端查重当并发锁。
- `src/dsh-client.js` 已允许调用方传入固定 `requestId`；省略时每次生成新编号。旧 `deliverPromptNow` 没有传入持久编号，新调度不能直接沿用该重试方式。
- `session/cancel` 保留 inbox。现有 `stopSessionWork` 会先查询并移除队列，再 cancel；删除队列失败时仍尝试 cancel，但最终报告失败，不能据此认定旧任务已清干净。

选择：第一版不依赖运行中 steer。普通事件先落库并合并；短等待通过工具返回可见新事件；其他提醒在回合安全边界递送。`quietMs` 保持 12 秒硬上限。让出执行不清除当前场景。

恢复规则：投递前持久化 sessionId、requestId、消息范围与状态。传输异常标记结果未知，先核对原 inbox/历史及回合状态；不能换 requestId 或新建 session 来重试。源代码去重证据不等于已经验证完整冷启动、压缩后历史恢复；这一组合留作新版集成验收。

### V02 / V04：场景和未读

代码证据：`src/bridge.js` 的 `deliverPrompt` / `processPromptQueue` 按 key 排队；`peakSleepBlocksV2` 拦普通场景每次投递；`readThroughSeqV2` / `acknowledgeMessagesV2` 使用连续水位；入站队列按 `unreadLimit` 淘汰旧项。

因此新模式需要独立场景策略和持久化未读账本，不能复用旧峰期总拦截，也不能把短数组长度当永久未读数。旧模式保持原逻辑。

设计契约：

- join 在准备结束、状态提交前再次校验峰谷、身份和准入；提交串行化。失败保留原场景，成功才增加进入代次并撤销旧凭证。
- 发消息按实际外部发送逐条核验账号、当前代次、权限和暂停；已发部分保留回执，不因切换改目标。已经交给上游的动作不能假装撤回。
- 菜单快照是明确略过的依据；展示回执和总结委托绑定消息集合。三者不授予发送权，不能只用最大序号越过未读空洞。
- 峰期隐藏其他普通场景时，旧菜单快照及晚到总结不能继续消费这些消息。已进入场景跨回合、等待及可靠重启恢复后保留资格，退出后不恢复资格。
- 未读记录采用持久化事件与确认范围；30 是批次默认大小。过去已被旧队列淘汰的内容不能凭空恢复；迁移清楚标出历史缺口，不制造“已经处理”的记录。

以上为实现契约，新的并发切换、跨峰快照及完整未读账本尚未实现或通过测试，须在基础模块落地时以 A15、A24—A28、A41—A50 验收。

### V03：全局权限

代码证据：`modePreset` 仅给真实 owner 私聊选择 `qq-chat-v2-files`；`plugins/qq-agent-presets/qq-tool-restrict-files.mjs` 精确放行受限文件工具，但不检查动态权限等级。现有文件 MCP 是 preset 内直接挂载的 Filesystem 服务。

因此，新主 preset 不能原样继承这个直连文件入口。采用桥接鉴权的文件工具适配层，再调用原受限 Filesystem 实现，保留原工作区和精确工具名单；不开放 shell、任意 MCP、额外移动或删除文件能力。v3 的“全部已有能力”不扩大原有文件工具集合。

主 Agent 使用稳定工具面；运行时每次核验全局等级，所以降级无需重建主 session。新主 preset 屏蔽直连 Filesystem 和宿主工具；v1/v2/v3 与人工暂停、身份变化及工具开关都在实际执行入口检查。原预设继续服务旧模式，不能为了统一模式放宽它们。

`dsh-tools` 的 `tools.guard` 是同步检查，不能假设给它传异步 HTTP 鉴权函数就能可靠阻塞执行。新模式选独立适配入口，不将远程异步鉴权塞入旧同步守卫。

文件适配层的真实路径、符号链接、异步撤权及同一 session 降级拒绝，必须在该层实现后验证；本轮只证明旧入口需要适配，不声称新授权链已经运行。

### V05：辅助总结

安装包 `dsh-tool-subagent` 支持 `agentPreset` / `allowedAgentPresets`，spawn provider 支持不继承父上下文的独立 preset；默认未指定 preset 可能继承父 preset。现有 QQ 守卫明确禁止原生 subagent/fork，不应直接解除限制。

原生工具以 `delivery: parent` 启动任务，结果由 DSH 通知父 Agent；不能据此声称桥接已能推迟峰期隐藏场景的晚到结果。第一版选择需求已允许的替代方式：桥接管理受限总结 worker，主 Agent 通过限定消息范围的总结工具创建作业，桥接保存结果并按当前可见性决定何时递送。

复用 `src/shared-memory-worker.js` 的受限会话、事件收集和归档模式，但另设总结 preset 与作业状态。子会话不拿主令牌、发送工具、文件工具或自主已读权限；结果只包含受委托范围。旧 worker 的重启/未知投递/回收测试已通过，不代表新总结 worker 已实现。

### V06：QQ 空间

`src/qzone.js` 的 `run()` 当前把 browse、固定周期/评论唤醒、decide、动作执行及已读合在一次调度中。`src/bridge.js` 每 30 秒调用该入口。空间已有自己动态已读、评论/@ 独立记录、写前记账和未知结果不重发的保护，可复用。

选择：拆开“只采集并落事件”和“主 Agent 请求执行动作”。通知轮询不调用模型，不按采集完成自动读掉其他人的事件；删除统一模式下的独立 qzoneAgent 决策调用。真正发说说、评论及回复仍走原校验与账本，继承配置中的次数、间隔、可见性和功能开关。上游未提供的通知范围照实报告。

### V07 / V08：持久化和迁移

现有共同记忆 SQLite 保存经历、人物、长期认识、关注内容及整理进度，但不是统一未读/调度账本。新账本与既有记忆分开，避免为本次迁移改写已有记忆含义。主 session 沿用已有 QQ 工作区；临时总结 session 使用同一工作区和独立受限 preset。

普通压缩、502、413 不自动创建新 session。保留当前模型路由，先限制消息批次和媒体/工具输出体积，再使用现有上下文管理能力。跨模型压缩状态迁移不属于本次默认操作；冷恢复与压缩组合仍须集成验收。

迁移顺序：备份 → 停止旧调度新增投递 → 持久化交接事件与回执 → 清理旧 inbox 并等待旧动作终态 → 撤销旧桥接令牌/发送权 → 启用唯一新发送权。任何清理或未知动作无法核对时，保持等待并记录原因，不能同时开启两个发送者。旧文件执行也须完成或确认停止，不能仅归档会话就声称已停工。

回滚先撤销新发送权，再将新增事件、明确已读范围及成功回执衔接旧模式；不恢复一个过时快照覆盖新数据。旧协议表达不了的非连续已读范围须保留在兼容账本中，直到旧消费水位追上，避免已处理消息反复唤醒。完整交接/回滚模拟尚待迁移模块实现，禁止直接上线试错。

## 3. 模块与数据契约（拟采用）

采用独立目录和稳定接口接入 `bridge.js`，保留旧 reserved2 分支。以下名字为实现设计，不是已经存在的文件。

| 模块 | 职责 / 必须持久化的内容 |
| --- | --- |
| unified/store | 独立 SQLite 账本：账号、主 session 创建身份、全局等级、当前场景代次、未读事件、确认范围、关注项、作业、动作回执和交接状态 |
| unified/scheduler | 每账号一个主回合；事件去重合并；固定 requestId；pending / dispatching / accepted / unknown / completed；明确拒绝与未知结果分开 |
| unified/scenes | 菜单、join、quit、场景凭证；执行前复查准入、峰谷、暂停、账号及代次；失败 join 不清空旧场景 |
| unified/inbox | 真实未读数、默认 30 条读取、快照略过、逐消息/范围确认、总结授权；只读和已读分别记账 |
| unified/tools | 主身份令牌与场景凭证校验；聊天/Qzone 路由绑定目标；全局关系动作使用明确目标；v1/v2/v3 命令来自可信入口 |
| unified/files | 桥接授权后调用原受限 Filesystem，保持精确工具与路径边界；原直连入口不进入新主 preset |
| unified/summary-worker | 按需独立受限 worker；保存消息集合、作业编号、sessionId、结果和递送/确认状态；失败或隐藏不推进已读 |
| unified/migration | 账号级运行代次和单一发送权、暂停交接、旧令牌撤销、状态导入及可回滚衔接 |

账本内的事件身份至少包含账号、来源场景、上游消息/评论标识及事件种类；不能只用时间戳去重。动作先保存意图，再调用外部服务，最后保存真实回执；结果未知不能当作失败换编号重发。凭证在工具边界验证，持久化可信场景状态不等于永久相信模型持有的旧令牌。

## 5. 下一段工作的边界

实现基础账本、场景/权限策略与串行调度时，首先落实并运行跨峰、并发、暂停、身份变化、快照范围和断线恢复测试；完成后再接入新主 preset 与工具。随后接空间/总结/文件适配，最后实现迁移并进行禁止发送的演练。

本轮没有需要用户重新退出 QQ 的步骤，也没有必须更换 SnowLuma 的阻塞。尚未运行的新模块测试必须继续登记，不将这份技术方案当作实现完成。部署时需要加载新的桥接代码和 DSH preset/MCP；具体重载方式在部署准备完成后列明，本轮不执行重启。
